# Electric-motor winding temperature: a machine-learning virtual sensor

UCS321 · MST Mini Project #6 · General Electric (GE) Power Systems case study

Estimate the **stator-winding temperature of a permanent-magnet synchronous motor (PMSM)** from signals a
motor drive already measures (speed, torque, d-q currents and voltages, coolant and ambient temperature),
evaluated strictly on **operating profiles the model has never seen**, plus an experimental residual
monitor, a Streamlit dashboard, a report and a presentation.

> **Honesty notes.** The GE name comes from the academic problem statement. The data are public
> measurements from a **Paderborn University** test bench, *not* GE hardware. Results describe that motor
> and test bench only. The residual monitor is **not** a certified protection system and no fault-detection
> accuracy is claimed (the dataset has no labelled faults).

## Setup (Windows, Python 3.12, [uv](https://docs.astral.sh/uv/))

```powershell
git clone https://github.com/Aryaveer2103/ucs321-General-Electric-GE-Power
cd ucs321-General-Electric-GE-Power
uv sync                               # creates .venv from uv.lock
```

## Run

```powershell
uv run motor-thermal data             # download (kagglehub) / locate the CSV, validate, write provenance
uv run motor-thermal eda              # exploratory figures
uv run motor-thermal train --mode fast      # ~2 min smoke run on a subset (preliminary numbers)
uv run motor-thermal evaluate --mode fast
uv run motor-thermal train --mode full      # ~20 min on 12 CPU cores; full training profiles
uv run motor-thermal evaluate --mode full   # held-out test evaluation, plots, monitoring
uv run motor-thermal forecast --mode full   # optional 60 s-ahead experiment
uv run motor-thermal report --mode full     # report, viva numbers, diagram, PowerPoint
uv run streamlit run app/streamlit_app.py   # dashboard
```

Without internet/Kaggle access, download `measures_v2.csv` manually from
<https://www.kaggle.com/datasets/wkirgsn/electric-motor-temperature> and pass `--csv path\to\measures_v2.csv`
(or put it in `data/`, or set `MOTOR_THERMAL_CSV`). If the data cannot be found the CLI stops with a clear
message; it never substitutes synthetic data.

Quality gates:

```powershell
uv run pytest -q
uv run ruff check . ; uv run ruff format --check .
```

## Method in brief

* **Target:** `stator_winding`. **Never used as inputs:** `stator_winding`, `stator_tooth`, `stator_yoke`,
  `pm`, `profile_id` (enforced in code and tests).
* **Validation:** whole `profile_id` groups are assigned to train/validation/test (stratified by peak
  temperature; manifest in `artifacts/split_manifest.json`). Test profiles are read only by the final
  evaluation, after the model selection is frozen on validation profiles.
* **Track A (instantaneous):** current measurements + physics-derived features (i², |u|, mechanical power,
  loss proxy …) with baselines, Linear, Ridge, Random Forest, HistGradientBoosting and LightGBM.
* **Track B (history-aware):** adds strictly causal EWMAs/rolling means (30 s … 2 h) of i², speed, torque
  and coolant temperature to represent thermal inertia; offline and streaming implementations are tested
  to agree.
* **Monitoring:** residual = measured − estimated, causal smoothing, empirical band from validation
  profiles, persistence rule; sensitivity illustrated with synthetic offsets only.
